# 平台租户与数据源归属设计说明

## 这个设计解决什么问题

OpenClaw 的平台租户本质上是一个团队容器，真正使用数据的是租户下面的成员。

在接入 `kingdee_analytics` 这类上游业务库后，需要同时解决两件事：

1. 平台租户要先绑定一套数据源，租户里的成员才能使用这套数据
2. 同一个租户下，不同成员可能只能看部分组织，所以成员还需要单独配置 org 可见范围

如果不把这两层拆开，后续很容易把“谁拥有数据源”和“谁能看哪些组织”混成一个概念，导致权限模型越来越乱。

## 核心规则

### 1. 平台租户和数据源是一对一

- 一个平台租户只能绑定一套数据源
- 一套数据源也只能归属一个平台租户
- 绑定关系存放在 `tenant_data_source_bindings`

这样做的原因是，租户下面的成员共享同一套业务数据来源，成员之间的差异只体现在组织范围，不体现在数据源选择。

### 2. 成员不选择数据源，只配置 org 范围

- 成员没有修改租户数据源的权限
- 成员级权限只控制可见组织范围
- 组织范围配置挂在成员层，而不是挂在租户层

这样可以满足：

- 同租户下的成员共享一套账套数据库
- 不同成员可见一个、多个或全部组织

## 为什么保留两个不同的“租户”概念

### 平台租户

平台租户就是 OpenClaw 自己的团队租户，用来：

- 增加成员
- 分配 Agent
- 绑定数据源

### 上游租户编码 `sourceTenantCode`

`sourceTenantCode` 不是 OpenClaw 平台租户。

它只是数据源自身携带的上游元数据，用来描述这个数据源在外部业务系统里的租户/账套上下文。它不能代表 OpenClaw 里的归属关系。

真正的数据源归属必须看 `tenant_data_source_bindings`，不能看 `sourceTenantCode`。

## 为什么新增“创建数据源”页面

原来的数据源管理入口是平台租户页上的一个弹窗，适合做基础维护，但不够清楚地表达“创建后立即绑定租户”这条业务规则。

现在新增一个独立页面 `创建数据源`，目的是把这条规则显式化：

1. 先选择一个平台租户
2. 创建数据源
3. 立即完成绑定

这样平台管理员在创建时就能明确知道这套数据源归谁所有。

## 为什么保留租户管理里的“绑定数据源”弹窗

独立的 `创建数据源` 页面负责新增数据源和首次归属。

租户管理里的“绑定数据源”弹窗继续保留，原因是它更适合做租户维度的切换操作。比如：

- 某个平台租户要从旧账套切换到新账套
- 平台管理员要从租户视角快速查看当前绑定情况

因此两个入口分工不同：

- `创建数据源`：新增并归属
- `租户管理 -> 绑定数据源`：租户视角切换绑定

## 为什么连接驱动和 analytics 配置也走零侵入部署层

这套能力后续要单独提交、拉取和部署，不能依赖去改 OpenClaw 根工程里的 `package.json`、`pnpm-lock.yaml` 或 `docker-compose.yml`。

所以当前实际运行方式固定为：

1. `setup-direct-docker-compose-up.*` 在零侵入生成目录里单独准备 tenant sidecar 运行依赖
2. Postgres 驱动 `pg` 通过零侵入层自己的 runtime 目录挂进 `openclaw-tenant-platform`
3. analytics 相关环境变量也通过生成的 `docker-compose.override.yml` 注入 sidecar

这样做的结果是：

- 根工程源码保持不动
- fresh pull 后只要跑零侵入部署脚本，就能拿到完整依赖
- 平台租户绑定数据源、租户管理员配置 org 范围，这两条链路不会再偷偷依赖本地临时改过的根配置

## 对后续开发的约束

后续如果继续扩展这个能力，请保持下面几个原则不变：

1. 不要把平台租户归属写到 `sourceTenantCode`
2. 不要让成员拥有切换数据源的权限
3. 数据源切换后，要继续清理旧 org 范围，避免成员沿用错误组织权限
4. 平台租户与数据源的一对一关系，前端和后端都要同时校验
